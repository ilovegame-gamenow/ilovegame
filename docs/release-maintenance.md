# 発売日変更と発売前の再確認

## 目的と正本

作品はgames、機種・地域・正式発売／早期アクセスごとの予定はgame_releasesを正本とする。延期ニュースを見落とす場合に備え、保存した公式出典を発売前に再確認する。ニュースの掲載点数と、カレンダーの日付訂正は別の判断。記事化しない訂正も保存できる。

この変更はレビュー用。DB SQL・機能フラグ・定期タスクは、本番反映の承認後に有効化する。記事や既存の発売情報を初期移行で変更しない。

## 保存と反映

- `game_release_checks`：調査結果、取得できた根拠、確認対象の変更前の値、変更案、判断待ち／採用／不採用を保存する。
- `game_release_history`：game_releasesを変更した際の旧値・新値をDBトリガーで保存する。SQLで直接変更した場合も記録される。導入以前の履歴を捏造しない。
- `record_game_release_check`：安定したUUIDで確認結果を保存する。確認中に対象が変更されていたら競合を返す。情報の取得やAI推論中はトランザクションを保持しない。
- `resolve_game_release_check`：確認済みの同一作品の公式・ストア出典であることを再確認し、対象の1行だけを更新する。確認した時点の完全なスナップショットと更新日時を照合し、人の編集を上書きしない。反映・判断記録・変更履歴は同一トランザクションで保存する。同じ操作の再試行は二重反映しない。

延期後の新日付が確定した場合は`announced`と新日付。新日程未定は`delayed`・日付NULL・`unknown`、中止は`cancelled`・日付NULL・`unknown`とする。既存の公開カレンダーはdelayed/cancelledを除外するため、旧日付に掲載されなくなる。月／年予定は精度を保ち、仮の1日を確定日として表示しない。別機種・別地域・早期アクセスの行は変更しない。

登録済み出典の確認状態が取り消された場合は反映を拒否する。対象外の作品・地域・機種、未確認情報、時差による表示差は反映しない。日付しか分からない発表に時刻を作らない。Steamは日本語やcc=jpのみでJSTと判断せず、必要なら`timezoneOffset=32400,0`による日本時間表示を確認する。

## 再確認の間隔

間隔と対象選択は`list_game_release_rechecks(20)`に集約する。ChatGPTの既存6時間タスクが、実行時に期限を迎えた行を取得する。別の常駐処理・有料AI API・GitHub Actionsの収集は追加しない。最大20件はこの再確認の1回の処理量であり、ニュースの採用件数ではない。

| 対象 | 確認成功後の再確認間隔 |
| --- | --- |
| 発売日まで7日以内、および未確認のまま発売日を過ぎて7日以内 | 1日 |
| 発売日まで30日以内 | 3日 |
| それ以外の発売予定・日程未定の延期 | 14日 |
| 取得失敗・曖昧・未解決の変更案 | 6時間 |

最初は未確認分を対象とし、発売が近いもの・前回確認が古いものを優先する。発売済みと確認した行と中止は定期再確認から外す。単に日付を過ぎただけでは発売済みにしない。対象が多い場合は残件を次回に残し、網羅したと報告しない。同一作品・同一公式ページは一度取得して複数機種の確認に再利用してよいが、確認結果は各発売行に保存する。

## 定期タスクへ追加する実行手順（承認・DB適用後）

1. public関数とテーブルの存在を読み取りで確認する。未適用・権限不足なら停止／報告し、タスク自身でスキーマを作成しない。
2. ニュースから延期・中止・新日程を発見した場合は、既存のgame_id・機種・地域・release_kindに照合する。新しい記事を作るかどうかにかかわらず確認対象にする。
3. `select * from public.list_game_release_rechecks(20)`で通常の再確認対象を取得する。各行のupdated_atを文字列のまま保持する。元の公式URLの本文と、必要なら同じ作品の最新の公式告知を確認する。検索抜粋や古いキャッシュだけでは判断しない。日本向け・JSTの基準を維持する。
4. 新たな確認済み公式出典があれば、既存のgame_sourcesを再利用または追加する。出典と対象作品の一致、発表日時、対象機種、地域を確認し、内容を取得できない出典をverifiedにしない。旧告知を新情報として採用しない。
5. 通常のUUIDを生成し、`record_game_release_check`にp_id,p_release_id,p_expected_updated_at,p_source_id,p_outcome,p_proposed,p_reason,p_evidenceを渡す。p_proposedはstatus,release_date,date_precision,release_labelだけ。変更なしなら現状のこの4項目をそのまま指定する。取得失敗はunavailable、根拠が曖昧ならambiguousとしp_proposedはSQL NULL。読んだ一次情報の具体的な箇所・確認した日時／タイムゾーンをevidenceに記録する。
6. 公式に変更を確認できた場合だけchange_candidateを保存し、同じ確認結果のIDと対象の更新日時で`resolve_game_release_check(id,expected_updated_at,'apply')`を呼ぶ。明確な延期発表や国内公式の新日程を根拠とし、単なるストア表記差は自動適用しない。解釈に迷う場合はambiguousとして編集室で確認できるよう理由を残す。未解決を架空の日付で埋めない。
7. 反映後に発売行・checks・historyを再SELECTし、可能なら公開カレンダーAPIを確認する。競合したら同じ候補を強制反映せず、新しい現状から再確認する。各作品の変更／変更なし／確認不能／競合／残件を分けて報告する。

既存タスクの「異なる既存発売日は上書きしない」という制限は、この確認・履歴・競合保護を通した公式変更の採用に限り置き換える。既存記事の更新禁止・採点基準・API不使用・タスクのスケジュールは維持する。

## 編集室と段階的な公開

作品管理ページ内の「発売日の確認・変更履歴」にまとめる。ページや設定を別々に増やさない。公式の変更案を確認し「反映」「不採用」を選べ、再確認対象と最近の履歴を同じ場所で読める。`release-maintenance-preview.html`は同じ表示部品を使う架空データの見本で、DBには保存しない。

承認後の適用順：`database/game-release-maintenance.sql` → 権限・RPC読み取り確認 → コード反映と`GAME_RELEASE_MAINTENANCE_ENABLED=true` → 既存保存タスクにこの手順を追加 → 現在の発売予定で読み取り再確認を1回行う。フラグ未設定時は新機能だけ503となり、既存の記事・カレンダー・作品管理は利用できる。

テーブルはRLS有効でサーバー専用。関数はSECURITY INVOKER、search_path空。anon/authenticatedへの表・関数権限は与えない。変更履歴にservice_roleのUPDATE/DELETE権限を付けない。
