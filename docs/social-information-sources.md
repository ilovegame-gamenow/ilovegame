# SNS・動画をゲーム情報の参考にする設計

## 今回の変更

設定の追加候補にYouTube、X、Threads、TikTok、Bluesky、Reddit、Instagramを追加し、SNS・動画・コミュニティとして同じ一覧内に分類する。実際のAPI接続・収集・保存・採点は今回追加しない。アプリの申請、アカウント接続、有料契約も行わない。

## 役割と取得条件

| 情報源 | 使いたい情報 | 実装前に確認する点 |
| --- | --- | --- |
| YouTube | 公式予告・ゲーム映像、公開日時と再生等の反響 | 単純集計と独自スコアの条件は区別。保存・更新期限、API枠を確認 |
| X | 公式発表、公開投稿の反応 | API利用料・検索範囲・保存と削除への追従 |
| Threads | 公式発表、作品に関する公開投稿 | キーワード検索等の権限、審査、取得可能な指標 |
| TikTok | 短いゲーム映像と反応 | Display APIは許諾したクリエイターの情報が中心。Research APIには用途・適格性条件があり、商用サイトの横断検索にそのまま使えると考えない |
| Bluesky | 開発者の発表、公開の感想 | 公開APIと各エンドポイントの認証・回数・利用条件を確認して少量試行 |
| Reddit | 作品別コミュニティの具体的な感想 | データアクセス承認・商用利用条件を確認。公開WebページとAPI利用許可を混同しない |
| Instagram | 公式投稿・Reels | APIはプロアカウント向けの範囲が中心。一般投稿全体を収集できる前提にしない |

2026/11/01時点で公式資料を調査。ThreadsのMeta開発者ページは429で本文取得できず、Metaの公式Postmanコレクションで検索APIの存在を確認した。広範な取得権限・取得指標・審査条件は、実装前に一次資料で再確認する。制限の回避を目的とした取得方法は採用しない。

## 作品への紐づけ

SNSの反応は作品の事実情報を直接上書きしない。作品IDを中心に、公式情報・反応の資料・編集者/AIの見立てを分ける。

将来の反応資料には次を持たせる設計を検討する（今回DB変更なし）。

- game_id、platform、external_id、出典URL
- 動画/投稿の公開日時と、こちらが確認した日時
- 公式発表、利用者の体験談、発売前の期待、判断できない資料の区別
- 指標の種類と元の数値。非公開・未取得は0件に置き換えず、不明とする
- 収集条件：対象期間、検索語、言語、取得上限、取得件数。標本とプラットフォーム全体を区別する
- 利用・保存条件の確認状態と、再取得/削除が必要になる時期

作品名だけで決めず、公式URL、ストアID、開発元、映像内容などで別作品・同名作品・続編を確認する。誤対応や未確認資料は候補のまま保持する。

## 偏りを抑える表示

- SNSごとの生の指標を分けて見せる。同じ1万回でも再生の定義・経過時間・媒体・投稿形式が違うため、単純に合算した関心度は作らない。
- 再生数を人数・購入意欲・ゲーム品質と呼ばない。コメント数だけで好評/不評を判断しない。
- 公式予告と実際の体験談、再投稿と独立した意見を区別する。複数プラットフォームに転載された同じ話を、独立した裏付けと数えない。
- 広告や提供の有無は明示されている情報で確認する。数値から広告視聴や自然流入の内訳を推定しない。
- 攻撃的な言葉を代表意見として抜き出さず、具体的な遊び・操作・不具合などの指摘と前提を確認する。
- 反応の少ない作品は「資料が少ない」であり、低品質という評価にしない。
- 削除/非公開になった内容に追従し、個人の属性や閲覧履歴を集めない。作品の紹介に必要な公開資料に絞る。

## 段階的な進め方

1. 今回：一覧へ追加し、接続条件と情報の役割を整理する。
2. YouTubeの公式動画とBlueskyなど、条件を満たす少量の読み取りから検証対象を決める。必要なアプリ登録・許可・費用を先に確認する。
3. 編集室だけで作品への対応と資料の読み方を確認する。自動採用・自動公開はしない。
4. 公開表示の文案・件数・取得時点・出典を確認してから公開方法を決める。
