# 発見候補の確認と作品台帳への採用

AI収集に先立って、発見した情報を確認する待ち受け先を作る。
今回は手動登録・候補一覧・重複の手掛かり・保留・採用まで。AIの呼び出し・定期収集・追加課金は開始しない。

## データの責任

`game_discoveries` は未確認の発見情報を保存する。作品名、原題、出典で確認した概要、面白そうな点、出典URL／種類、取得日時、取得元、調査メタデータ、確認状態、採用先を持つ。
`games` と `game_sources` が採用後の作品・出典の正本。候補の採用で記事本文・掲載状態・発売日を自動更新しない。
面白そうな点は候補の判断材料として保持し、作品の紹介文へ自動転記しない。

状態は `pending`（未確認）→ `held`（保留）または `adopted`（採用済み）。保留は未確認に戻せる。採用済みは履歴として保持し、別作品へ再採用したり保留に戻したりしない。

同じURLに複数作品が載ることがあるため、取り込み時の重複判定は正規化済みURL＋前後空白と大文字小文字を無視した作品名。
同じ候補が再度届いても、確認状態・説明・面白そうな点を上書きしない。
このキーは作品そのものの同一性を保証しない。和英名などによる別候補は残り、採用時に既存作品を明示的に選べる。
今回の重複手掛かりは作品名・原題の一致または同じ出典URL。完全一致以外の類似判定や外部IDによる自動同定は後続段階。

## 採用の原子性

`review_game_discovery` は対象候補を `FOR UPDATE` でロックする。

- 新規作品へ採用：既存 `create_editor_game` を呼び、作品と出典を作り、採用先を記録する。同じ候補の同時採用・再試行でも作品は1つだけ。
- 登録済み作品へ採用：その作品に出典を追加し、採用先を記録する。作品名・紹介文・既存出典の確認状態は維持する。
- いずれも途中で失敗すると、候補・作品・出典の変更をまとめて取り消す。
- 候補の採用は公開操作ではない。新規作品はdraft、追加出典はpendingのまま。

## コードと入口

API数を増やさず `/api/editor-games?resource=discoveries` で振り分ける。
`api/editor-games.js` に認証・POSTの同一オリジン確認を集約し、候補の処理は `lib/editor-discoveries-handler.js` に分離。
DB通信は `catalog-database` を作品・候補で共用する。候補の入力検証・repositoryもそれぞれ専用モジュールに置く。
画面は `editor-discoveries.html`。既存の作品管理CSSと `editor-catalog-client`（安全なDOM生成・UUID・認証付き通信）を共用する。
手動候補フォームは同じタブ内に途中入力と作成IDを保持し、セッション切れや通信失敗後にも同じIDで再試行できる。

## 権限と公開手順

新テーブルはRLS有効、PUBLIC/anon/authenticatedの権限なし。新RPCもSECURITY INVOKER・search_path空・service_roleだけにEXECUTEを許可する。
新しい `GAME_DISCOVERIES_ENABLED=true` がない場合、候補APIはDBに接続せず準備中と返す。既存作品管理のフラグと独立させる。

レビュー・ユーザー確認後に `database/game-discoveries.sql` をSupabaseへ適用し、本番のみフラグを有効にしてコードを反映する。
既存の作品・記事を移行したり削除したりする処理はない。現在の開発段階では本番DB・環境変数は未変更。

## 検証

既存のNode.jsテストに、候補の入力・認証・オリジン・無効時動作・ページ送り・RPC呼び出しの検証を追加。
`tests/database/game-catalog.sql` から候補SQLテストも読み込み、重複・確認状態の維持・採用途中失敗のロールバック・既存作品への採用・権限を検証する。
実PostgRESTの接続テストも既存ハーネスを共用し、同時採用・検索結果の重複手掛かり・匿名アクセス拒否まで確認する。
テストは隔離したCIのDBのみを使い、本番に候補や作品のテストデータを残さない。
