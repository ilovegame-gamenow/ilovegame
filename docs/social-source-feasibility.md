## Blueskyの実データ確認

開発元の公式ページが案内している`amongusstory.bsky.social`のみを対象とした。
確認元：https://www.innersloth.com/among-us-story-on-guard-demo-available-now/

- 公開AppViewのgetAuthorFeedを1リクエスト、limit=5、返信とピンを除く指定で読み取る。
- 公式アカウント本人の通常投稿か、URIの所有者と投稿者が整合するかを追加で検証する。再投稿、返信、重複、別アカウント、形式の違う記録を除外する。
- 読み取り結果：5件中4件が条件に一致し、1件は再投稿として除外された。
- 取得できた情報：元投稿のURL、公開日時、いいね数、再投稿数、返信数、引用数。未取得は0とせずnullにする。
- 今回は投稿本文やプロフィールを報告へコピーせず、作品IDも推測しない。DBや公開画面へ接続しない。
- 生の試行結果は一時確認のみ。リポジトリに投稿本文・個人プロフィール・統計履歴を固定保存しない。

費用面：今回の試行は公開エンドポイントへの読み取りで、APIキー・認証・有料契約なし。OpenAIも使っていない。公開APIのレート制限は守り、将来も常に無制限・無料と保証する設計にはしない。既存Vercel/Supabaseの利用枠は別に確認する。

## YouTubeの最初の取得案

1. メーカー/開発元の公式サイトで確認した動画URLを最大3本選ぶ。検索結果の動画を公式と推測しない。
2. 動画IDをまとめ、videos.listのsnippet/statisticsを1リクエストで読む。投稿・評価・アカウント操作はしない。
3. 公開日時、動画名、チャンネル、元URL、再生数、高評価数、コメント数、こちらの確認日時を表示する。非公開/無効/欠落は「取得できない」とする。
4. 初回は現在値だけを表示。独自の関心度スコアや、他SNSを混ぜた総合点、広告視聴数の推定を作らない。

必要な準備：Google CloudのAPIプロジェクトと、YouTube Data API v3を有効化したAPIキー。公開動画の基本情報を読む最小構成では、利用者のYouTubeアカウント権限や投稿権限は要求しない。キーはサーバー側に置き、API制限を掛ける。チャットや公開ブラウザーへキーを貼り付けてもらう運用にはしない。設定作業はユーザー確認後。

利用枠の目安：公式リファレンス上、videos.listは1リクエスト1 unit。動画3本をまとめる最初の確認は1リクエストを想定する。現行の既定枠はsearch.listとvideos.insertが各100 calls/day、それ以外の共通枠は10,000 units/day。実アカウントの割当を優先する。「1 unit」を金額と混同しない。枠の追加や有料サービスを申し込まず、既定枠内で最初の検証を設計する。

保存と集計：取得データの更新・削除期限を守る。一般の未承認データの30日更新/削除と、追加条件を満たす長期保存を区別する。過去時点の統計を現在値に差し替えて「過去履歴を更新した」とは扱わない。独自指標や長期履歴を追加する前に、派生指標・保存条件の適用範囲と必要な承認を確認する。

今回はYouTubeのAPIキーの作成・取得・設定も、YouTube API呼び出しもしていない。利用アカウント固有の請求条件と割当は未確認。

## 作品管理への接続案

- 設定の「情報源と収集」は接続状態・収集条件の唯一の管理場所にする。
- 作品管理の関連情報に、公式資料と利用者の反応を分けて表示する。別の設定ページを増やさない。
- 初期は元URL・公開日・確認日時・媒体ごとの元の指標を表示し、人が作品との紐づけを確認する。
- 名称だけで自動対応しない。Innerslothの別作品の発表をAmong Us本編の更新情報にまとめない。
- 公式アカウントの投稿に反応があることと、一般利用者の感想を収集したことを区別する。今回は後者の検証ではない。
- 投稿の数字を作品品質や購入意欲と断定しない。小さい取得件数から世間全体の評価を推測しない。

次の実装は編集室内の読み取りプレビューから。採用・記事作成・公開は自動で行わず、本番反映前には確認する。
